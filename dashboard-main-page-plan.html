01. Outcome and boundaries

Primary outcome

A user opening the product at / sees the Tablekeep brand, navigation for personal and rules-reference areas, and scannable campaign and character cards. The page should feel like the beginning of the real product, not a dashboard template.

Data outcome

Campaigns, characters, and feedback use typed tRPC procedures. The procedures return in-memory fixtures with stable IDs and ISO timestamps, making the response shapes the provisional contract for later Drizzle work.

Interaction outcome

Each dashboard section begins in a compact state showing the first three cards. Show all (n) reveals every remaining item independently; Show less returns the section to three.

Responsive outcome

Desktop uses a floating, icon-collapsible sidebar and a three-column card grid. Tablet moves to two columns. Mobile opens the sidebar as the existing sheet and renders a single readable card column.

Non-goals

  • No Drizzle tables, migrations, database reads, campaign membership logic, or seed scripts.
  • No campaign detail, character sheet, compendium, settings, or help-page implementation.
  • No copied rules text, monster stat blocks, or commercial compendium data.
  • No create/edit/delete flows for campaigns or characters in this pass.
  • No new package or alternate state-management library.
The sidebar may expose the final route vocabulary before those destinations exist, but the implementation must clearly treat those pages as planned. The dashboard itself, theme control, feedback interaction, external Help link, and sign-out action are the functional scope of this change.

02. Verified codebase findings

  • apps/web/src/app/page.tsx is still the Create T3 starter and currently performs one server-side api.health.check() call.
  • apps/web is the correct workspace for this authenticated product surface. apps/docs remains the static marketing and documentation site.
  • packages/ui/src/components/sidebar.tsx already exposes SidebarProvider, Sidebar, SidebarInset, SidebarTrigger, groups, menus, footer, tooltips, cookie persistence, the Ctrl/Cmd+B shortcut, and mobile sheet behavior.
  • The shared sidebar accepts variant="floating" and collapsible="icon". The official sidebar-04 block uses the floating variant and a 19rem provider width.
  • Shared cards, collapsibles, dropdown menus, avatars, badges, dialogs, skeletons, separators, tooltips, and buttons already exist in packages/ui; application-specific compositions belong under apps/web/src/components/.
  • packages/ui/src/icons/tablekeep.tsx provides the current-color Tablekeep tower mark. @tabler/icons-react is already installed for the navigation icon set.
  • apps/web/src/components/providers/index.tsx already configures tRPC/TanStack Query, next-themes, tooltips, and toasts.
  • Better Auth exposes authClient.useSession() and authClient.signOut() through apps/web/src/server/better-auth/client.ts.
  • The tRPC root currently contains only health.check. Both publicProcedure and protectedProcedure are available, but public mock procedures are the correct temporary choice so this dashboard does not depend on an authenticated database session.
  • The main checkout contained apps/web/.env. It has been copied into this worktree as an ignored file without exposing its contents. The main checkout did not contain a local apps/docs/.env.

03. Dashboard experience

Navigation model

Brand header

Use TablekeepIcon in a compact violet tile next to Tablekeep. When the sidebar is icon-collapsed, retain the tower mark with a tooltip and hide only the wordmark.

Personal

Campaigns and Characters, with whichever destination route is current visibly active. On the root dashboard both remain neutral and the brand link carries the current-page state. Use final hrefs /campaigns and /characters.

Wiki

In order: Races, Backgrounds, Classes, Spells, Monsters, Feats, plus Items and Conditions. Keep this as a labeled, scrollable group rather than nested accordions.

Footer

Help opens the public documentation in a new tab, Feedback opens an in-app dialog, and a full-width user row opens the account dropdown.

User menu behavior

  • Show session avatar, name, and email when Better Auth has a session.
  • Use a clearly named preview user fixture when no session exists, so local mock development remains complete.
  • Provide a Settings link targeting /settings.
  • Provide Light, Dark, and System choices backed by useTheme(); show a check beside the active choice.
  • Call authClient.signOut() for a real session, show success or failure through the existing toaster, and refresh/redirect to / after success. In preview mode, label sign-out unavailable instead of pretending to terminate a session.

Section reveal rules

visibleCount = expanded ? items.length : Math.min(3, items.length)
hiddenCount  = Math.max(items.length - 3, 0)

0 items      → directional empty state; no Show all control
1–3 items    → render all items; no Show all control
4+ items     → default to first 3; button reads “Show all (hiddenCount)”
expanded     → render all items; button reads “Show less”

Campaigns and Characters keep separate local expanded state. Use an actual Collapsible root/content relationship for accessible state and animate only a short opacity/height transition that respects reduced motion. Do not persist this state; a new visit returns to the compact overview.

Card content

Campaign card

Name, short summary, game-system label, the user’s role (DM or Player), party/member count, active character count, and next-session date or Not scheduled. The full card links to /campaigns/[slug].

Character card

Name, ancestry, class list with levels, total level, linked campaign or Unassigned, portrait/initials, and HP only when the endpoint provides it. The full card links to /characters/[slug].

Mock six items per section so the initial state visibly hides three and exercises the exact Show all (3) behavior requested.

04. Visual direction

The subject is a busy in-person tabletop session, the audience is players and DMs, and the page’s single job is to get them back into a campaign or character quickly. The visual language should feel like a clean campaign folio: compact, tactile, and calm enough to scan while people are talking.

Palette reference

  • Keep navy #24324F — grounded brand detail.
  • Arcane violet #7047EB — active and focus accent.
  • Ember orchid #D673C4 — restrained secondary accent.
  • Mist #F3F5F6 — light dashboard canvas.
  • Ink #20252B — light-mode text.
  • Night #171A20 — dark dashboard canvas.

These are visual calibration values. Implementation should extend the existing semantic OKLCH tokens in apps/web/src/styles/globals.css, not scatter raw hex colors through components.

Type

Keep the existing Inter face for headings, labels, and body copy. Use JetBrains Mono only for levels, dates, counts, section eyebrows, and compact game metadata. This preserves brand continuity and makes changing table state easy to scan.

Layout

A 19rem floating sidebar sits eight pixels from the viewport edge. The content inset uses a restrained max width, generous horizontal breathing room, and two stacked sections whose three-column grids align.

Signature detail

Give each card one narrow, asymmetric ledger tab edge derived from its stable mock accent. It evokes dividers in a campaign binder without adding fantasy ornament, parchment texture, gradients, or decorative noise.

05. Mock API contracts

Create domain routers rather than importing JSON directly into the page. Keep fixtures in a server-only mock module, mark the procedures and data as temporary, and do not access ctx.db. Use publicProcedure only while the responses are fixed fixtures; replacement procedures must become protectedProcedure and verify ownership/membership when persistence arrives.

Provisional response types

type CampaignSummary = {
  id: string;
  slug: string;
  name: string;
  summary: string;
  gameSystem: { id: string; name: string };
  role: "dm" | "player";
  memberCount: number;
  activeCharacterCount: number;
  nextSessionAt: string | null; // ISO 8601
  accent: "violet" | "orchid" | "navy" | "teal";
  updatedAt: string; // ISO 8601
};

type CharacterSummary = {
  id: string;
  slug: string;
  name: string;
  ancestry: string;
  classes: Array<{ name: string; level: number }>;
  totalLevel: number;
  campaign: { id: string; name: string } | null;
  portraitUrl: string | null;
  hitPoints: { current: number; maximum: number } | null;
  accent: "violet" | "orchid" | "navy" | "teal";
  updatedAt: string; // ISO 8601
};

type ListResponse<T> = {
  items: T[];
  total: number;
};

Procedures

  • campaign.listMine(): ListResponse<CampaignSummary> — return six fixtures in intentional display order.
  • character.listMine(): ListResponse<CharacterSummary> — return six fixtures, including one multiclass character, one unassigned character, one missing portrait, and one null HP value.
  • feedback.submit(input) with { category: "idea" | "issue" | "other"; message: string; page: string }; validate a useful message length and return { accepted: true, reference: string } without persistence.

Fetch campaign and character lists concurrently in the server page with Promise.all, then pass typed results into the interactive shell. This exercises the same API boundary a future database implementation will preserve without introducing a client waterfall. Derive hidden counts from items.length, not the fixture’s total, while the endpoint remains unpaginated.

Mock data must be clearly fictional and contain only short original summaries. Do not include proprietary rules prose or published character/monster content.

06. Component architecture

apps/web/src/app/page.tsx (server)
├── Promise.all(campaign.listMine, character.listMine)
└── DashboardShell (client)
    ├── SidebarProvider
    │   ├── AppSidebar
    │   │   ├── brand header
    │   │   ├── PersonalNav
    │   │   ├── WikiNav
    │   │   └── footer: Help, FeedbackDialog, UserMenu
    │   └── SidebarInset
    │       ├── compact dashboard header + SidebarTrigger
    │       ├── DashboardSection<CampaignSummary>
    │       │   └── CampaignCard × visibleCount
    │       └── DashboardSection<CharacterSummary>
    │           └── CharacterCard × visibleCount

Keep AppSidebar, dashboard sections, cards, feedback, and account menu in apps/web because they encode Tablekeep routes and game data. Reuse primitives from @tablekeep/ui without changing shared components unless a verified primitive defect blocks the composition.

Server/client boundary

  • Keep page.tsx as a Server Component responsible for API calls and top-level metadata-friendly content.
  • Mark only the shell/compositions that need sidebar state, section expansion, theme selection, session hooks, feedback mutation, or routing hooks as client components.
  • Pass serializable API results into the client shell; ISO date strings avoid hydration ambiguity.
  • Format dates with an explicit locale/options on both server and client, or only inside the client card components, to prevent markup mismatches.

07. Ordered implementation steps

  1. Define fixtures and tRPC contracts

    Add the provisional summary types and six deterministic fixtures per domain in a server-only mock module. Add campaign.listMine, character.listMine, and feedback.submit routers and compose them in appRouter. Keep the existing health route.

  2. Establish the dashboard shell

    Replace the starter page with concurrent server-side tRPC calls. Build a client DashboardShell using SidebarProvider, a 19rem Sidebar variant="floating" with icon collapse, and SidebarInset. Ensure the mobile trigger remains visible.

  3. Compose the application sidebar

    Add the tower brand header, Personal and Wiki groups in the requested order, active-route handling through usePathname(), unique Tabler icons, collapsed tooltips, and the bottom Help/Feedback/account area. Keep the navigation config as typed data rather than repeated JSX.

  4. Wire Help and its environment boundary

    Add NEXT_PUBLIC_DOCS_URL to apps/web/src/env/client.ts with the local default http://localhost:3001/docs. Add the documented placeholder to apps/web/.env.example and update docs/development.md. The copied local env can omit it because the schema supplies the local default.

  5. Build account and theme interactions

    Create the avatar user menu using Better Auth’s session hook, a clearly labeled preview fallback, Settings link, theme radio/check items, and real-session sign out. Add suppressHydrationWarning to the root <html> if needed by the theme class.

  6. Build the feedback dialog

    Compose existing dialog, select, textarea, button, and toast primitives. Validate category/message client-side, call the mock mutation, close and reset on success, and preserve the message on failure.

  7. Build the reusable progressive-reveal section

    Implement an accessible section header, total count, independent default collapsed state, hidden-count calculation, and Show all (n) / Show less control. Support empty and short lists without empty grid slots or misleading controls.

  8. Build domain cards

    Compose campaign and character cards from the shared Card primitives. Apply the ledger-tab accent, readable metadata hierarchy, full-card links, hover/focus parity, null-safe dates/HP/portraits, and responsive grid behavior. Keep all displayed copy short and original.

  9. Align product metadata and tokens

    Replace the generated page description in apps/web/src/app/layout.tsx, correct the web font token binding to the already loaded Inter/JetBrains variables, and add only the minimal Tablekeep accent/surface tokens required for the dashboard in apps/web/src/styles/globals.css.

  10. Verify behavior and inspect formatter output

    Run the narrow app type check first, then workspace checks. Because pnpm check writes safe Biome changes, inspect git diff afterward and keep only relevant formatting. Exercise desktop, mobile, light, dark, collapsed sidebar, both section states, feedback success, and session/preview account states.

09. Risks and edge cases

Mock authorization drift

Fixed public responses are acceptable only because they contain no private data. Add an explicit replacement note beside each procedure: future data must use protectedProcedure and server-side ownership/membership checks.

Dead navigation

The requested sidebar names future destinations. Keep target hrefs in one config and visually distinguish destinations that are not implemented in this pass; do not suggest that planned compendium content already exists.

Hydration and theme flash

Theme state is client-derived. Use the established next-themes pattern, delay active-theme checkmarks until mounted if necessary, and suppress only the root class mismatch.

Nested interactive controls

If the whole card is a link, do not place buttons or menus inside that anchor. Use a stretched-link pattern or keep secondary actions outside the link target.

Responsive density

Three visible cards is a content rule, not a row rule. On mobile it becomes three stacked cards; on tablet it may span two rows. Do not hide items based on CSS breakpoints.

Unknown and null data

Dates, campaign assignment, portraits, and HP are nullable by contract. Cards must render a useful label or omit a row without shifting the rest of the grid into broken alignment.

10. Validation strategy

Automated checks

  • pnpm --filter web check-types
  • pnpm check-types
  • pnpm check, followed by git diff --check and a diff review
  • pnpm --filter web build when the local database/auth environment permits it

Manual desktop checks

  • Open pnpm dev:web at http://localhost:3000 and confirm no starter content remains.
  • Verify the floating sidebar spacing, 19rem expanded width, icon collapse, tooltips, active state, and Ctrl/Cmd+B.
  • Verify both sections begin with exactly three of six fixtures and display Show all (3).
  • Expand one section and confirm the other remains compact; then test Show less.
  • Verify campaign/character card focus rings match hover affordances and all metadata is readable.
  • Submit valid feedback and confirm toast/reset behavior; verify invalid text is rejected without losing the draft.
  • Switch Light, Dark, and System modes and reload to confirm persistence and no severe theme flash.
  • Verify Help opens the configured public docs URL and Settings targets /settings.

Responsive and accessibility checks

  • At approximately 375px, verify the sidebar opens as a sheet, focus remains trapped, and the dashboard is one column without horizontal scrolling.
  • At tablet width, verify a two-column grid and readable section controls.
  • Navigate the entire shell, reveal controls, dropdown, theme choices, feedback dialog, and cards by keyboard only.
  • Confirm visible focus, meaningful labels/tooltips, decorative icons hidden from assistive technology, and no duplicate link/button nesting.
  • Enable reduced motion and confirm reveal/sidebar behavior remains clear without required animation.
  • Inspect light and dark contrast for muted metadata, active nav, violet focus, and ledger-tab accents.

Contract checks

  • Call each tRPC procedure and confirm the inferred output matches the provisional types.
  • Temporarily exercise empty, three-item, four-item, and more-than-six-item arrays against DashboardSection.
  • Confirm no router reads ctx.db, no schema file changed, and no migration was generated.
  • Confirm fixture IDs/slugs are stable, list totals match fixture lengths, and timestamps are valid ISO 8601 strings.
